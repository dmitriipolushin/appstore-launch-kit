# Decision Gates

**Читать перед шагом 4. Каждая рекомендация должна пройти соответствующий gate.**

---

## GATE 1 — Поднять бюджет?

Две проверки, строго в этом порядке. Расход ниже 90% лимита **сам по себе не означает**,
что бюджет поднимать не надо.

**Проверка 1 — не занижен ли бюджет в абсолюте.** Считай, сколько установок бюджет вообще
разрешает купить: `daily_budget ÷ CPI`.

Слишком низкий дневной лимит — это сообщение алгоритму Apple «нам нужно всего несколько
установок в день», и открутка пессимизируется. Кампания не откручивает даже свой маленький
лимит именно потому, что лимит маленький.

> Пример: CPI $2 при бюджете $6/день = «мы готовы купить 3 установки». Поднятие лимита
> до $12 может дать фактический расход $10 — не потому что разрешили больше, а потому что
> перестали ограничивать алгоритм.

- `daily_budget ÷ CPI` меньше ~5 установок → **raise budget обоснован даже при расходе ниже 90%**
- Поднимать примерно вдвое и смотреть **фактический** расход через день, а не ожидаемый
- Если после поднятия расход не вырос — вот теперь ограничение в аукционе, идти в GATE 2

**Проверка 2 — упирается ли расход в лимит.** `spend_7d ÷ 7 ÷ daily_budget × 100%`

- ≥ 90% → кампания budget-limited → **raise budget обоснован**
- < 90% **при бюджете, который уже даёт ≥ 5 установок** → кампания auction-limited →
  бюджет не поможет, нужен raise bid (GATE 2)

Правило «не поднимать бюджет при расходе < 90%» действует только после Проверки 1.

## GATE 2 — Поднять ставку?

Выполнить **все три проверки** по порядку:

**2a. IS проверен?**
- Если IS-отчёт ещё не запущен → запусти его сейчас (шаг 3.4), не предлагай bid raise без IS.
- Исключение: кампании с 0 impressions — IS не нужен, сразу +$0.20.

**2b. IS < 90%?**
- IS < 90% → raise bid обоснован
- IS ≥ 90% → ключ у потолка, raise bid не поможет → **предложи новые ключи вместо raise**

**2c. CPTrial приемлемый?**
- CPTrial < $20 → raise bid обоснован
- CPTrial > $20 при > 15 installs → сегмент дорогой, raise bid усилит убыток → **сначала пауза или оптимизация страницы**
- < 5 installs → мало данных, CPTrial не считать, raise bid допустим

## Потолок ставки — ориентир, а не граница

`economics.by_geo.<GEO>.bid_ceiling` в конфиге проекта (обычно `breakeven_cpa / 0.9`
или `target_cpa / CR тап→установка`) — **ориентир для фактической цены тапа, а не предел
ставки.** Правило кита с 2026-10.

- **Ставка выше потолка допустима и часто нужна.** Аукцион второй цены: ставка — это
  готовность платить, а списывается ставка следующего участника + $0.01. Высокая ставка
  даёт показы, а фактический CPT при этом остаётся на уровне потолка или ниже. Обрезать
  ставку до потолка — значит терять показы, не экономя на цене тапа.
- **Сам потолок плавает.** Он пересчитывается из конверсии тап→установка и ARPU, а обе
  величины на малых выборках прыгают в разы. Жёсткая граница по такому числу режет
  трафик из-за шума.
- **Что сравнивать с потолком — фактический CPT, а не ставку.** Сигнал — CPT за период
  **устойчиво** выше потолка: на ≥ 5 тапах и не один день. Тогда — GATE 3 по фактической
  экономике (CPI, триалы/выручка), пересчёт потолка, точечное снижение ставки по
  решению пользователя. Ставка выше потолка при CPT ниже потолка — нормальное состояние.
- **Инструменты ставку до потолка не обрезают и не понижают.** `scripts/asa/bids.py`
  показывает рядом ставку, потолок, фактический CPT и флаг `CPT > потолка`;
  `adgroups.py` на ставку выше потолка печатает предупреждение. Жёсткий предел —
  только явный `--max-bid`, если его задал пользователь.
- **В плане изменений** указывай для каждого ключа ставку, потолок и фактический CPT,
  а не «ставка упёрлась в потолок».

## GATE 3 — Паузировать?

Пауза обязательна при любом из условий:

| Условие | Действие |
|---|---|
| 0 impressions при bid ≥ clearing price **3+ дней** | Pause — нет объёма в аукционе |
| > 15 installs + 0 trials | Pause — сегмент не монетизируется |
| trial rate < 3% при > 15 installs | Pause — аудитория не конвертится в платящих |
| 0 installs при taps > 15 | Pause keyword — трафик нерелевантен |

**Диапазоны ожидания — два пути:**

**Если триалы есть (≥ 1):** считай CPTrial = spend / trials. Пауза если CPTrial > max_cptrial.
max_cptrial = LTV × TTP — читать из `unit-economics/asa_pause_strategy.md` каждую сессию, не хардкодить.
CPI сам по себе не повод для паузы — высокий CPI при хорошем trial rate может быть окупаемым.

**Если 0 триалов:** порог зависит от CPI (чем дороже установка, тем быстрее пауза):

| CPI | Пауза при 0 триалах |
|---|---|
| ≤ $1.50 | После **15 installs** |
| $1.50–$2.50 | После **10 installs** |
| $2.50–$3.50 | После **5 installs** |
| > $3.50 | После **3 installs** |

> Источник: `unit-economics/asa_pause_strategy.md`

## GATE 4 — Тест BROAD: предлагать? оставить?

По умолчанию все ключи — EXACT. BROAD — только тест; полное описание —
`asa_campaign_architecture.md` → «BROAD — только как отдельный тест».

**4a. Предлагать тест** — нужен хотя бы один повод:
- фраза из 3+ слов на EXACT: 0 показов 3+ дня при ставке на уровне потолка-ориентира или выше,
  но в подсказках App Store у неё много вариантов (`hits`);
- ядро исчерпано: IS ≥ 90% у работающих EXACT-ключей (GATE 2b) и новых ключей не находится —
  нужен дополнительный объём установок.

Не повод: «найти новые формулировки запросов». Запросы, пойманные BROAD, Apple скрывает
как low volume (`(none)`) даже в крупных гео — цель теста только установки по приемлемой цене.

И все предпосылки:
- фраза из 3+ слов (1–2 слова в BROAD — нет);
- у кампании есть экономика EXACT за 7+ полных дней — база для сравнения;
- в кампании нет работающего Discovery (Search Match) с той же задачей;
- план согласован: фразы, ставка, негативы, лимит расхода теста, дата оценки.

**4b. Оценка** в дату теста или при исчерпании лимита расхода:

| Результат | Действие |
|---|---|
| CPI/CPTrial не хуже EXACT кампании, установки EXACT не упали | Оставить |
| Любое условие GATE 3 | Пауза BROAD-адгруппы |
| Экономика хуже EXACT кампании при ≥ 10 установках | Пауза BROAD-адгруппы |
| Среди видимых search terms в основном чужой интент | Негативы адгруппы, затем повторная оценка |
| EXACT-ключи кампании потеряли показы/установки после старта BROAD | Пауза: негативы не держат, BROAD каннибализирует |

Решение принимается по экономике (строки 1–3, 5). Search terms — только для негативов: большая часть запросов скрыта как low volume.

## Пороги для оценки

**IPM** = installs / impressions × 1000

| IPM | Оценка |
|---|---|
| > 15 | Хорошо |
| 8–15 | Нормально |
| < 3 при 30+ impr | Проблема воронки |
| 0, taps > 0 | CR проблема (страница) |
| 0, taps = 0 | CTR проблема (bid / объявление) |

**CPTrial**

| CPTrial | Оценка |
|---|---|
| < $5 | Хорошо — масштабировать |
| $5–10 | Приемлемо — наблюдать |
| $10–20 | Дорого — оптимизировать |
| > $20 | Пауза |

**Trial rate**

| TR% | Оценка |
|---|---|
| > 15% | Сегмент монетизируется хорошо |
| 8–15% | Нормально |
| 3–8% | Слабо |
| < 3% при > 15 inst | Пауза |

**TTR**

| TTR | Оценка |
|---|---|
| > 3% | Хорошо |
| 1–3% | Приемлемо |
| < 1% при 100+ impr | Объявление нерелевантно |
